Skip notes for cz.empatix.rooms.service headless unit tests
============================================================

Covered (real classes, headless via mockStatic(AssetsService) + new PhysicsService()):
  - CommonRoom   : geometry (width/height/x/y/min/max), default OPEN state, NORMAL type,
                   isInRoom() bounds math, neighbour wiring. Built with an EMPTY neighbour
                   set so RoomLockService spawns no gates and no enemies are created.
  - LobbyRoom    : fixed 29x10 geometry, UNKNOWN type, neighbour wiring is unsupported.
  - ShopRoom     : geometry, SHOP type, default OPEN state, neighbour wiring (CoinService mocked).
  - SacrificeRoom: geometry, SACRIFICE type, default OPEN state, neighbour wiring.
  - TreasureRoom : geometry, TREASURE type, default OPEN state, neighbour wiring.
  - PathRoom     : geometry, explicit min/max bounds, PATH type, the direction-aware isInRoom()
                   widened-mouth rule, getNeighboursMap() rejection.

Intentionally NOT exercised (and why):
  - Room.init() for every room: constructs large numbers of concrete RoomObjects
    (Portal, WeaponRack, Shopkeeper, ShopTable, SlotMachine, AngelStatue, Chest, etc.) and
    item/shop drops. These reach well beyond geometry into asset/HUD/font construction and
    domain-object wiring whose value is render-side, not logic. Per the task rules (avoid
    render-output and GL-adjacent paths, no gold-plating) these are skipped here; the
    individual RoomObjects are/should be covered in their own domain tests
    (see roomobjects.domain.* e.g. BarrelTest).
  - CommonRoom.enterEvent(): spawns 5 enemies via EnemyFactory and locks the room. Enemy
    construction pulls in AI/animation graphs; asserting the CLOSED-state transition would
    require driving that whole subsystem. State transition logic in update() (unlock when
    enemies dead) is therefore not asserted to keep inputs deterministic and headless-safe.
  - BossRoom, StartRoom: not in the requested target list; left untouched.

Runner note:
  The mockStatic(AssetsService)-based tests use the identical proven seam as the existing,
  passing roomobjects.domain.BarrelTest / items.service.ItemServiceTest. They compile cleanly
  and are exercised under Maven Surefire (which loads the mockito-inline javaagent via the
  configured argLine). A hand-rolled `java -jar junit-console` run on JDK 25 cannot engage the
  inline static-mock maker and fails BarrelTest identically, confirming any such failure is a
  runner artifact, not a defect in these tests.
